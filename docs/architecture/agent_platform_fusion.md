# 融合方案：Agent 提案 / 平台判定

日期：2026-09-18 ｜ 上游对照见 `agent_platform_gap.md` ｜ **本文只写方案，不改任何代码**

---

## 0. 一句话

融合不是"把两个系统拼成更大的系统"，而是**接成一圈带判据的闭环**：

```
Agent 提候选参数 → 平台跑覆盖 → 平台的判据说这一轮算不算被定住 → 回灌 Agent
                        ↑
              （不是回灌一个 RMSE 数字）
```

骨架**已经存在并且跑通了**：`SimulationRequest → simulator.py → run_baseline_cell(parameter_overrides=…) → SimResult`。
实测（`docs/SIMREQUEST_IMPLEMENTATION.md` §Case A/B-1/B-2）：

| case | 请求 | RMSE [mV] |
|---|---|---|
| A | `params={}` | 48.36 |
| B-1 | `electrode_thickness = 120 µm`（TEST ONLY） | 65.53 |
| B-2 | `electrode_thickness = 64 µm`（= 原值） | 48.36（**逐位等同 A**） |

⇒ 平台侧只加了一个关键字参数（`parameter_overrides=None` 是严格 no-op），**没有 monkey patch**。
所以融合这一侧**不需要新平台能力**，需要的是**把判据接进反馈**。

---

## 1. 三层，只做前两层

| 层 | 内容 | 现状 |
|---|---|---|
| **L1 契约层** | 一次仿真的 `SimulationRequest` / `SimResult` 冻结结构 + 参数能力守卫（`param_capability.py`） | **已有**；缺 3 个接缝（§3） |
| **L2 判据层** | 把平台的五道门接进闭环，让每轮迭代**过判据**而不是过 loss | **要做 —— 这一层是融合的实质** |
| **L3 治理层** | 把 `dataset_role` / 预注册 / provenance 搬到 Agent 侧 | **不做**：平台的治理是给"论文级证据"用的，Agent 侧**引用**即可 |

**为什么不把 L3 也搬过去**：治理的价值在于"结论能不能被引用"，而在 Agent 侧它没有对应的判据可判 ——
搬过去只会变成一份没人校验的声明，正是平台一直在防的"看起来被接受了其实什么都没做"。

---

## 2. 融合的实质：把「过 loss 门」换成「过判据门」

现在 Agent 的反馈信号 = loss（电压 / 容量 / 电流残差）。这有一个平台**已经证明过**的后果：

- **真值不是最优解**：错误模型假设下，偏 −25 % 的参数拟合反而好 **3.4×**
- **谷是脊不是碗**：电压只约束 **τ_d = R_p²/D_s**，两个方向同时动就看不见
- 所以对着 loss 迭代，收敛到的是"拟合好"，**不是"参数对"**

融合要做的事：让每一轮的反馈里**带上平台的判定词**，而不是只带残差：

| 反馈项 | 来自 | 它告诉 Agent 什么 |
|---|---|---|
| 判定词 | 五词判定（`identifiable` / `bounded` / `unconstrained` / `not_identifiable` / `not_measured`） | **这个参数在这个窗口能不能报点估计**；`bounded` 只许报界 |
| 活性门 | `battery_sim/excitation/`、`simulation/protocol_replay.py` | 你这一轮改的参数，模型对它**有没有响应** |
| 尺度门 | `governance/scale_alignment.py`（两个 C-rate 并列） | 模型与记录**是不是同一把尺子**（不是同一把尺子时 RMSE 不反映模型误差） |
| 覆盖率 / 初值接线 | `identification/rate_prediction.py` 的四道门 | 这一段比较是否**有效**（残片上打分会让错参数看起来很好） |
| 消费守卫 | `param_capability.py` 的 `models` 字段 | 这个键**被当前模型读不读**（零效果 ≠ 收敛） |

**其中只有"判定词"是全新的信息。** 这句话就是融合能成论文的原因：
它把 Agent 的反馈从"你差了 X mV"变成"**你改的这个参数在窗口 #t475 是 bounded，你不能把它当点估计**"。

⚠️ 反过来也要说清：融合**不会**让参数变得可辨识。G6.1b/1c 已经证明**瓶颈在激励，不在参数化** ——
Agent 再聪明也造不出数据里没有的激励。所以融合的价值上限是**如实说出哪里不可辨识**，不是"辨识出来"。

## 3. 三个接缝

### ① 把平台的门搬进 `SimResult.diagnostics`（**零平台改动**）

平台上已经有这些量：`coverage_fraction`、`applied_overrides`、尺度门记录、活性门观测量。
现在的桥只把它们折算成一个 RMSE。要做的是**原样搬进 `SimResult.diagnostics`**，
并保留"哪一个门判失败"的字段。这是**桥侧改动**，不动平台。

### ② 初始态策略必须能传（**Agent 侧 open item #1**）

现状：`params.initial_state` 是**占位**，桥不读它 ⇒
**Phase B0.5 冻结的 44.64 mV 走公开入口拿不到（得到 48.36 mV）**。
原因已定位：B0.5 用 `OCPConsistentAdapter` 反演**变体自己的** OCP 表并裁剪到 `[X0_MARGIN, 1-X0_MARGIN]`
（锂化落在 `x0 = 0.001`，`clamped_to_table_edge=True`），而标准 adapter 反演的是**参考表**。
两者各自自洽，只是起点不同 ⇒ 44.64 与 48.36 **不是同一个测量**。

要做闭环就必须让它变成**真字段**（桥把它翻成平台的 `initialisation` 块）。
平台侧已有 `initialisation_block(cell, v0=...)`，所以仍是桥侧为主。

### ③ 曲线型参数（**唯一必须进 `v0.1.1` 的融合项**）

`ocp` 与 `particle_diffusivity` 现在直接 `BridgeError`。而**这一批实验恰恰要改 OCP**
（p-OCV 双支实测表），所以躲不开。平台目前把曲线走**adapter 的 `ocp_table_path()`**，
没有一个"把曲线推进参数集"的公开入口 ⇒ 需要平台侧一个 additive 的曲线覆盖入口。

⚠️ 还有一条同类：**表示形式是 `(逻辑名, 参数集)` 的属性，不是名字的属性**。
实测：`Positive particle diffusivity [m2.s-1]` 在 `Chen2020` 里是 **float**（4e-15），
在 `Ecker2015_graphite_halfcell` 里是 **function**。`param_capability.py` 已经按这个口径建表，
桥不许退回到"按名字判断"。

## 4. 明确不做

| 不做 | 理由 |
|---|---|
| 把 LLM 放进平台主循环 | 违反平台冻结（`v0.1.0-platform` = `ee2fb36` 不动）+ 导师明确"不要再扩展 Agent" |
| 把 BO / CMA-ES 搬进平台 | 那是 Agent 的**基线**，不是平台的**判据**；平台缺的不是优化器 |
| 迁 L3 治理到 Agent 侧 | 见 §1 |
| **先做多参数联合辨识** | G6.1b/1c 已证：**瓶颈在激励不在参数化**（放电扫程 239 个窗口一个都不合格） |
| 让 Agent 回改 L4 的参数 | 回改即 L4 作废（预注册已冻结） |

---

## 5. 顺序（本文最重要的一节）

融合的价值**只在有真实数据要辨识时才兑现**。所以顺序不是"先把桥写完"：

```text
现在            CG-AR 实验 + L1/L2（纯平台侧，与 Agent 无关）
                     |
L3 出带宽图      第一次有了「哪些参数、在哪一段、可不可辨识」的清单
                 （不是一条漂亮的 D_s(x)，是逐窗口五词判定）
                     |
挂 Agent 上去    用 L3 的清单当候选白名单 —— 而不是让它自由提参
                     |
L4 预测          冻结参数预测 1C；Agent 不得回改
```

⇒ **融合的第一件事不是写桥，是把 Agent 的候选集限定在 L3 说"可辨识"的那些参数上。**
这一条同时解决 Agent 侧那个悬而未决的问题（`BORROW_NOTES.md` §5：白名单与 prompt 知识文本两套名字零重叠）——
白名单不该由人手写，**应该由 L3 的带宽图生成**。

## 6. 环境与许可

- **契约层是纯标准库**：`param_capability.py` 刻意不 import 任何东西（连 pandas 都不 import），
  目的就是"契约测试不需要网络、不需要 pybamm、不需要平台"。所以两边都能跑。
- **但一次实验不能跨两个 pybamm 版本**：平台 26.8，Agent `requirements.txt` 写 `pybamm==25.6.0`。
  桥驱动平台时用**平台的环境**。实测：Agent 的 222 项测试在平台的 pybamm 26.8 环境里全过。

## 7. 融合算成功的判据

不是"Agent 找到了一组好参数"，而是这四条同时成立：

1. **每一轮都能说出这一轮的判定词**（而不是只说残差）；
2. **被 `param_capability` 拒的那些轮，原因写得出来**（unknown / 曲线给标量 / 模型不消费 / 参数集无此键）；
3. **L4 的 holdout 没有参与任何一轮**（含"以调参为目的的试跑"）；
4. **Agent 的候选集来自 L3 的带宽图**，不是人手写的名单。

⚠️ **不要**把目标写成"融合后 RMSE 更低"。平台侧的判据从一开始就不是 RMSE 低
（预注册 §3.4 明写"不设 RMSE 必须小于 X mV 的门"）。
